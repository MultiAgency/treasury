# The app server

`apps/server/` is the Treasury app's own server, on the platform's app route (`/apps/v1`): its own package in the pnpm workspace, Node running TypeScript directly, `node:http`, `@multiagency/sdk` 0.5.3 and `near-kit` 0.20.2. It holds the deployment's `tap_` credential and calls the platform with `appClient`; the browser only ever reaches this server's `/api/` routes. It was designed in #20.

- **Owner sign-in:** a NEP-413 challenge addressed to this server, verified with `near-kit` before any chain call, then a full-access key of the signing account on chain (FastNEAR's RPC, configured as the platform's `src/chain.ts`). Challenges are stateless (the nonce carries its issue time and an HMAC under a per-process key), so issuing one stores nothing and a flood can't crowd out an owner's; each is single-use once validly signed (only its canonical base64 text is accepted) and expires in 5 minutes. Challenges and sign-in attempts are each rate-limited per client (an IPv4 address, or an IPv6 /64).
- **Sessions:** a `Secure`, httpOnly, `SameSite=Strict` cookie, ended after 30 minutes idle, 12 hours or sign-out, and swept when abandoned; in memory, so a restart signs everyone out. Signing in again ends the previous session, and sign-out always clears the cookie, with or without a body. Every write checks `Origin` and requires JSON.
- **Per-agent authorization:** every `/api/agents/:agent` route checks that the signed-in account is the agent's owner, as the platform answers it, and that the agent's identity names this deployment. The platform allows a credential 1,200 calls an hour, shared by every owner, so a successful answer is reused for up to a minute per agent (never a failure, so an agent set up a moment later is reachable at once), concurrent reads share one call, and each account may make 60 owner-route requests a minute. A reused answer that would refuse the account is read once more anew, so a new owner isn't locked out after a transfer. Routes that answer from the server's own records, and writes that build on the agent's identity, always read it anew (`owner-fresh`). A missing agent and someone else's get the same answer, `not_owner`; any other platform failure is `unavailable`, as is an identity naming another deployment (this server misconfigured). The platform's error text is logged, never sent to the browser.
- **Connecting an agent:** the server builds the consent text from the agent's identity as the platform answers it now (for a wallet owner `read`, `treasury` and `owner` for 90 days, with no choice to make, under the owner's Organization: their account with each `.` written as `--`; a DAO's consent never carries `owner`. A connection made before this default, without `owner`, keeps working and is offered "Allow owner actions" (which replaces the connection and so withdraws its open proposals); when it is renewed, the new consent includes `owner`), and the owner's wallet signs it for the platform's host. An agent already connected isn't offered another signature. The server relays only that exact consent, submits the same signed body once more if the answer is lost, revokes the owner's older consents for the agent once a new one is stored, and limits each account to `CONSENTS_PER_DAY` new consents (the platform caps a deployment's live consents at 1,024, shared by every owner). A consent counts as the agent's only for its current ID, with `read` and `treasury` (and `owner` or not), unrevoked and unexpired. Disconnecting revokes those, at most five a request, found in the platform's own list, never by an ID from the browser.
- **Setup (#12):** an account with no Treasury signs the server's setup text (a Treasury agent for its own Organization, good for an hour, for the platform's host); the server relays only that exact text to `/apps/v1/setup`, sending the same body once more if the answer is lost. The platform reserves the agent and stores a setup consent that lets the server relay only its creation: `agent_create`, naming the key that signed the setup, which the owner signs on the platform's confirm page; the page follows it by `owner/status`. A DAO sets up by its own vote instead (`daoSetups`, filed and stored like its consent), then votes on the creation, which must pass within minutes. `GET /api/setup` lists the agents the account's consents name, set up or created; the setup routes count against the account's requests a minute.
- **Proposals:** the owner lists and reads their agent's proposals, under their own Organization only. They may ask for a rebalance to the saved strategy, proposed as `watch` proposes one (the strategy's legs, open for a day) under a `requestId` the page names: after a lost answer the page finds it by that ID, never asking again. Approving or rejecting relays the owner's wallet signature over the SDK's `proposalText` of the proposal the page shows; the server reads it anew first and refuses, with nothing relayed, unless it's unexpired, still open and exactly that text, signed with a full-access key of the owner for the platform's host. Execute is sent only for an approved proposal, once per request, and never again after a lost answer: the proposal is read and answers `final`, `pending` (offer no Execute; read it again later) or `not_executable` (nothing was sent; it may be tried later). The platform claims a proposal once, so it never runs twice.
- **Owner reads (#61):** the agent's overview, activity, payouts held, operations without a proven outcome, and the autopilot's runs and one run's recording, each one platform read under the owner's consent. A proposal is found by its `requestId` among the agent's proposals (the platform has no lookup by it), and an operation's status by its `correlationId` from its activity row, never `owner/status`, which answers `unknown` for any swap. Every `bigint` the SDK reads goes out as its exact decimal string. No live consent is `not_connected`; any other failure, a thrown call included, is `unavailable`, and the platform's text stays in the log.
- **Freeze and unfreeze** (#133): `POST /api/agents/:agent/freeze` and `…/unfreeze` prepare the owner action (`owner/prepare`) for a wallet owner to sign here (an intent), on the platform's confirm page, or for a DAO member to file for the vote, whichever the platform answers; `POST …/owner/actions/:id/submit` relays a wallet owner's signature once, `GET …/owner/actions/:id` follows it by `correlationId`, and `GET …/owner/pending` relays `owner/pending`. Each is audited before and after (`freeze`, `unfreeze`, `owner-submit`) and never sent again for a lost answer. A freeze and an unfreeze hold each other (`action_pending`) while one is submitted or a DAO's request awaits its vote; an intent that was only prepared isn't held, so a reload mid-signature never delays an emergency stop. A wallet owner needs a connection that allows owner actions (`owner_not_allowed`). The page's control is in the frame of every agent page (`EmergencyStop`); it reads the overview (frozen or not), `owner/actions` and `owner/pending`, each not within half a minute of the last, and every ten seconds only while one awaits its outcome.
- **Grant revocation** (#142): `POST /api/agents/:agent/grants/revoke` with `{ grantId }` prepares a `grant_revoke` the same way a freeze is prepared (intent, confirm page or DAO transaction), recorded as audit action `grant-revoke`. A revocation is held only by another revocation whose outcome is unknown (submitted, or a DAO request waiting for its vote); a freeze does not hold it. A wallet owner's connection must allow owner actions (`owner_not_allowed`).
- **Policy** (#134): `POST /api/agents/:agent/policy` with `{ expectedPolicy: { revision, digest }, changes }` prepares a `policy_update` through the same code (audit action `policy-update`), held only by another policy edit whose outcome is unknown. An edit that leaves the policy as it is is refused with `no_change` before anything is prepared; a DAO member without filing roles is refused with `not_permitted` before anything is prepared. For a DAO the answer carries `policy.current` and `policy.requested`, which the page shows beside each other before the member files (the DAO's proposal is public and names only the fields). `GET …/policy-history` relays the revisions and the mandate digest. The vote has about 290 s, or 600 s for an edit that changes an on-chain field (platform#20).
- **The Home's and Activity's reads** (#130, #136): `GET /api/agents/:agent/dao-requests` lists the DAO requests waiting for a vote on the agent (its consent, and its verdicts on proposals), from this server's own store with no platform call and no settling (a wallet owner's agent has none); `GET /api/agents/:agent/activity.csv` relays the ledger's CSV once, as a download (`ledgerCsv`); `GET /api/agents/:agent/owner/actions` relays `owner/actions` once, the platform's record of the owner's actions across devices. The Home adds at most three platform reads a visit (the proposals, the strategy and the autopilot, cached a minute, none polling); the Activity page's history is paged in the browser, 50 rows to a page, from the one `activity` read.
- **Funding:** the agent's funding account (`treasury/get`) and its own account (`account`) are owner reads. A deposit address (`deposit`, USDC or NEAR as wNEAR) is asked for by anyone who may file proposals, and a wallet owner links, unlinks or marks the funding account confidential, each relayed once. A DAO agent's funding account is the DAO, fixed at setup: the server refuses a member's change (`dao_funding_fixed`) whatever their roles. The platform's refusal is `funding_refused`, its text logged.
- **Strategy and autopilot:** the owner saves a strategy over the one they saw (`strategy/save` with its digest, checked against the platform's own rules first): autopilot turns off and the grant no longer binds it, and a strategy changed meanwhile is `strategy_changed`, never overwritten. For a DAO, saving needs members who may file and vote on its policy changes. The saved strategy (`strategy/get`: its digest, whether the held grant binds it, and why the schedule can't start) and the schedule (`autopilot/get`) are owner reads. Autopilot is turned on for the strategy digest the owner saw, turned off, or run once now (`autopilot/tick`), each relayed once and recorded; the platform's refusal is `autopilot_refused`. Disconnecting turns a wallet owner's autopilot off first, since once disconnected the owner has no page here to do it: a schedule that can't be read or isn't confirmed off revokes nothing (`autopilot_not_stopped`). A grant binding the saved strategy (`grant_issue`, label `treasury`, for the digest the owner saw) is prepared only once the strategy is read again: not for a changed strategy, with autopilot on, on an approve-only host, or while another grant waits. A wallet owner's connection must allow owner actions; their wallet signs its intent, which the server relays once, and the page follows its status. A DAO's member files it for the DAO's vote, which must pass within minutes. `watch` still holds while autopilot is on.
- **Sweep and books:** a sweep previews the managed public balances or shields them into the agent's private balance, sent once and read to its end. It's answered as the run's [AG-UI](https://docs.ag-ui.com) 1.0 events (`@ag-ui/core`'s schemas), delivered whole as JSON: `RUN_STARTED`, an `ACTIVITY_SNAPSHOT` of `treasury.sweep` after each event the platform gave, then `RUN_FINISHED`, or `RUN_ERROR` with the failure's kind as its `code`. A stream lost after it began has no terminal event: a truncated run, read as unknown, and never sent again. The books (`reconcileBooks`) are an owner read.
- **Audit trail:** every relayed setup, creation, consent, revocation, approval, rejection, execute, deposit address, funding-account change, shield, rebalance asked for, autopilot turned on or off or run now, grant prepared or submitted, and strategy saved is recorded in `TREASURY_AUDIT_FILE`, a JSON line before the platform is asked and one with its answer: who, what, the SHA-256 of the signed text, the platform's status and the code the browser got, never a signature. The log is a hash chain (`src/chain.ts`): each record carries the hash of the one before, so an edit, a removed record or a reordering is found, and the server won't start on a broken chain, if it can't append to the file, or if others can read it. A log in the old plain format is moved aside under a timestamped name at startup, never deleted.
- **Decisions and their replay (#54):** every decision `watch`'s Ballast step makes goes to the same log before anything acts on it, as a `decision` record with every input it was made from: the oracle reading, the engine's input (portfolio, bounds, DCA units used, anti-whipsaw state, regime) and config, the intent, the policy's context, config and result, and for a trade the policy let through, its size in cents and the legs made at the recorded prices. A hold is recorded too. A decision that proposes also names the `requestId` its request is then stored and sent under (#172), so a proposal on the platform traces back to the decision that made it; a recorded `requestId` with no request or proposal under it was never stored (the stored requests were full, or the server stopped first). Replay ignores it: it isn't an engine input or output. A record that can't be appended stops the tick, so nothing is proposed unrecorded. `pnpm --filter @treasury/server check:replay <audit log>` (in the deployed image, `node src/replay-check.ts /data/audit.jsonl` from `apps/server`) verifies the chain, replays every decision through the engines (`packages/core/src/decisions.ts`), and names the first record whose intent, policy result or proposal differs, by its sequence number.
- **Audit anchor (A7.3, #55):** with `TREASURY_ANCHOR_ACCOUNT` and `TREASURY_ANCHOR_KEY_FILE` set, the log's sequence number and head hash go on NEAR at startup and then every `TREASURY_ANCHOR_INTERVAL_S` (an hour by default), when something was recorded since the last anchor; after a day with nothing new, the last anchored head is sent again, unrecorded, so an outside check can tell a quiet deployment from a stopped one. The anchor is a FastData KV write: `contextual.near` (or `contextual.testnet`, with `TREASURY_ANCHOR_NETWORK=testnet`) calls `__fastdata_kv` on itself with `{"audit/<TREASURY_DEPLOYMENT>": {"v":1,"seq":<n>,"hash":"<64 hex>"}}`, so FastData's indexes keep every anchor of this deployment with its transaction hash. It's signed with a function-call key limited to that account and `__fastdata_kv`, in a 0600 file; the key attaches no deposit and can't move funds. The send waits for its receipts, so a failed call is never recorded; the log then records the transaction, and a failed anchor is logged and tried again next interval. `checkAnchors` reads each recorded anchor back by its hash through FastNEAR's archival RPC (a regular node forgets a transaction after a few epochs), so a log cut short or rewritten after an anchor is found. Testnet anchors go to FastNEAR's testnet RPC; sign-in and DAO reads stay on mainnet.
- **The anchor check (#55):** a scheduled GitHub Actions job (`.github/workflows/anchor-check.yml`, hourly), away from the server, that trusts neither the server nor its log. It reads every value FastData KV lists under the key (`POST /v0/history/<account>/<account>` with `include_metadata`), confirms each one by its transaction through FastNEAR's archival RPC, and fails when one isn't an anchor the chain confirms, when the sequence goes back or names one record with two hashes (a log rewritten and anchored anew), or when the newest anchor is older than a day, two intervals and ten minutes of index lag. With no anchor yet, it passes only within that allowance of `ANCHOR_SINCE`, when the deployment began anchoring; unset, an empty history fails, since it can't be told from a broken anchorer or a wrong key. It can't run while FastData KV or the RPC is down, and says so rather than passing. It checks `ANCHOR_KEY` (`audit/multiagency-treasury`, the deployment's) on `ANCHOR_NETWORK` (testnet) for `ANCHOR_ACCOUNT` (`contextual.<network>`), set as repository variables with `ANCHOR_SINCE`. Given a copy of the log (`pnpm --filter @treasury/server check:anchors --log <file>`), it also refuses a log that records an anchor outside the key's history, or that no longer has a record an anchor names.
- **The proposals page:** with `TREASURY_PAGE_DIR` set to the page's build (`web/dist-proposals`), the server serves the owner's proposals page from its own origin. It reads the build's regular files into memory at startup (no dotfiles or links) and serves them by exact path, for GET and HEAD: every other path outside `/api/` and `static/` is the page, which is never cached, may not be framed and sends no referrer. The page calls only this server's `/api/` routes.
- **`watch`, the proposer (#2):** with `TREASURY_WATCH_FILE` naming its agents, the server proposes a rebalance for each one when its holdings drift past the agent's threshold (5 points of the total by default), every `intervalS` (300 by default). It proposes only: with `legs: "strategy"` by this drift rule, or with the strategy engine's own legs for an agent configured with it (below). The owner approves on the proposals page. It holds while the agent has unresolved operations, while autopilot is on, while the policy isn't in force, and while a proposal of its own is still open. Each request is stored in `TREASURY_REQUESTS_FILE` before it's sent, and a lost answer is sent again unchanged, so it never makes a second proposal. If the owner's consent ends, the agent waits until they connect again. `notify`, a command and its arguments, runs without a shell, once per notice, with the notice as JSON on stdin and only `PATH` in its environment. Every payload names its `kind` and carries `organization`, `agent` and `page` (the agent's page, or the proposal's page for a proposal's kinds):

  | `kind` | Sent | Also carries |
  | --- | --- | --- |
  | `proposed` | a new proposal was made | `proposalId`, `expiresAt`, `secondsLeft`, `points` (the drift) |
  | `holding` | `watch` starts holding the agent, or the reason changes | `reason` (`unresolved-operations`, `autopilot-on`, `policy-not-in-force` or `consent-ended`) and `detail` |
  | `resumed` | the hold ends | |
  | `expiring` | one of its own proposals still awaiting the owner's answer has under an hour left, or under 10% of its life if that's shorter (and never less than one tick interval, so a tick always lands in it) | `proposalId`, `expiresAt` |
  | `expired` | one of its own proposals expired, whether nobody answered it or it was approved and never executed (sent before its request is forgotten) | `proposalId`, `expiresAt`, `approvedAt` (null when it was never answered) |
  | `approved_not_executed` | one of its own proposals was approved and not executed: an hour after approval, or when it enters its expiring window, whichever comes first, so a stuck one is reported before it expires | `proposalId`, `expiresAt`, `approvedAt` |

  A change is announced once, never on every tick: holding while autopilot is on is a normal state. What was sent is recorded before it is sent, in the requests file (`TREASURY_REQUESTS_FILE`, for a proposal's notices) and beside it in `<TREASURY_REQUESTS_FILE>.holds` (why each agent was last reported held), so a restart doesn't send it again; a notifier that fails is reported in the tick's log line and not retried. An agent with no `notify` sends and records nothing. `intervalS` must be shorter than a proposal's life (`proposalHours` × 3600 seconds), which the server checks when it loads the file: `watch` can't follow a proposal that lasts less than one interval. None of this adds a platform read: the notices come from the proposal each tick already reads and from the reads that decide a hold. The server won't start if the agents' reads would spend more than half the platform's 1,200 calls an hour (3 a tick).
- **The strategy engine (#47, [ADR 3](adr/0003-engine-parameters.md)):** an agent given a `ballast` object in the watch file (`profile`: conservative, balanced or growth; `monthlySpendUsd`, `operatingCashMonths`, `destinations` and `approvers`) is proposed for by the strategy engines (`packages/core`) instead of the drift rule (`src/ballast.ts`). Each tick, the platform's price goes through the oracle, the band engine and the policy to one swap proposal with explicit legs, or a reason to hold. Every proposal is still the owner's to approve: a level that asks for a human (L2, L3 sells) proposes, and one that refuses (L3 buys, L4) proposes nothing. Its only price source is the platform's `overview`, so its oracle runs on one source (`OVERVIEW_ORACLE`). The price history and the engine's state are kept beside the requests file (`<TREASURY_REQUESTS_FILE>.history`, `.engine`), and `node src/seed-history.ts <TREASURY_REQUESTS_FILE>.history`, run with the server stopped, seeds 35 days of hourly NEAR-USD closes from Coinbase, so the 30-day EMA needn't wait a month. Such an agent must tick at least hourly (`intervalS` at most 3600), which the server checks when it loads the file.
- **DAO-owned agents (#100):** a member of the DAO that owns an agent signs in as themselves, and is admitted by the DAO's policy (`get_policy`, read at most a minute ago) through the SDK's `accessOf`; each route also asks for what it needs (`mayCall`'s rules). The DAO's consent, and its verdict on a proposal, are filed for its vote (`daoConsents`, `daoVotes`), once per subject, stored before they're shown (`TREASURY_DAO_REQUESTS_FILE`); members file the platform's transaction from their own wallet or vote in Trezu. The server finds what the DAO already filed by matching its proposals' kind, never their description, and reads open requests every minute (at most five a pass, the least recently read first), so a vote that passed is completed in time. Filings are capped per member a day (`DAO_FILINGS_PER_DAY`).
- **Configuration** is checked at startup (`src/config.ts`); secrets print as `[secret]`, and a variable set to nothing counts as unset. This server's origin must be https except on localhost, since the session cookie is `Secure`. The credential file must be 0600; it's checked on every call and read again when it changes, so rotating it needs no restart. The rate limits use the connection's address unless `TREASURY_TRUSTED_PROXY_HOPS` says how many reverse proxies to trust for `X-Forwarded-For`.

## Running it

```sh
pnpm --filter @treasury/server typecheck
pnpm --filter @treasury/server test          # in-process, with fakes for the platform and the chain
pnpm --filter @treasury/server test:stack    # against fresh stacks started with --app, one with a DAO-owned agent (--dao-treasury)
pnpm --filter @treasury/server test:sandbox  # the on-chain key check against near-kit's local NEAR node; not run in CI
```

To run it, set `TREASURY_PLATFORM_ORIGIN`, `TREASURY_DEPLOYMENT`, `TREASURY_CREDENTIAL_FILE`, `TREASURY_PUBLIC_ORIGIN`, `TREASURY_AUDIT_FILE` and `TREASURY_DAO_REQUESTS_FILE` (and optionally `TREASURY_PAGE_DIR`, `TREASURY_WATCH_FILE` with `TREASURY_REQUESTS_FILE`, `FASTNEAR_API_KEY`, `NEAR_RPC_URL`, `TREASURY_TRUSTED_PROXY_HOPS`, `OWNER_REQUESTS_PER_MINUTE`, `CONSENTS_PER_DAY`, or `TREASURY_ANCHOR_ACCOUNT` with `TREASURY_ANCHOR_KEY_FILE`, `TREASURY_ANCHOR_INTERVAL_S` and `TREASURY_ANCHOR_NETWORK`), then `pnpm --filter @treasury/server start`.

On Railway it runs from the `Dockerfile`, with secrets as variables written to their 0600 files at startup: see [deploy.md](deploy.md).
